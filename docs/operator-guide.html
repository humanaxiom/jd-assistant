01

What JD Bank is

JD Bank turns SFU's sprawling job-description archive into a clean, governed source of truth — and helps staff author new, standards-compliant JDs.

The pipeline (back office). Every JD is parsed, de-duplicated, clustered by role, and harmonized into one draft canonical JD per role, scored by a deterministic validator. Run on the server via make tasks.

The app (front office). A web UI where people compose a JD with live compliance feedback, review & approve drafts, browse dashboards, and (admins) manage users.

The four guardrails — never work around these

Guardrail 1

Nothing auto-publishes

A canonical JD stays a draft until a human reviewer approves it. Overriding a blocking gate needs a written, recorded reason.

Guardrail 2

Self-hosted inference only

All AI runs on SFU-controlled Ollama (aria-gb10-2). No JD text ever reaches a cloud/vendor API — build-enforced.

Guardrail 3

The validator is the oracle

Scores and approvability come from the rulebook validator, never from the LLM's own claim about its output.

Guardrail 4

Tamper-evident audit

Every review action and every login is written to a hash-chained log — any alteration or deletion is detectable.

02

Personas & roles

Hiring manager / recruiter ✍ author
Use the Builder — search/clone, author, get AI assist, export .docx, submit a draft for review. Browse dashboards.
HR reviewer ✔ reviewer
Everything an author can, plus open the review queue and approve / reject / edit / override drafts — the human-approval gate.
System administrator 🔑 admin
Everything above, plus manage users — assign roles, enable / disable accounts.
System operator / DevOps 🖥️ operator
Run the pipelines, migrations, deploys and CAS config from the server shell. This is infrastructure access, not an app role.

New users are provisioned as author on first sign-in; reviewer and admin are granted by an admin. A person can be an app admin without server operator access — and the reverse.

03

Access & sign-in

  • Sign in with SFU CAS. The login page redirects to cas.sfu.ca and back; your identity is your SFU computing ID.
  • The nav bar shows your controls — 🧱 Builder · 📋 Review queue · 📊 Dashboards · 👤 Users 🔑 admins only · your name · Sign out.
  • 🖥️ operator Dev / CI mode (CAS_ENABLED=false): every request runs as a synthetic admin with no login, so the app is usable offline. Turn off in production.
  • 🖥️ operator First-admin bootstrap: set BOOTSTRAP_ADMINS=your-cas-id; those users are granted admin on login. That's how the first administrator is created — after that, admins manage everyone in the UI.
04

Authoring a JD — the Builder

🧱

Builder

👥 Any signed-in user · no admin

Where: /jd-bank/ui/compose/new

TaskHow
Start from an existing JD 🔎 Search to clone → pick a match → Start from this. Semantic search over the archive (JDFN scope). The form pre-fills.
Author from scratch Fill the guided questions, then Check compliance. The live panel shows score, grade, blocking gates, and fixes — each finding links to the section that needs it.
Improve the summary with AI ✨ Improve summary (assist) — a self-hosted LLM suggests a better Position Summary; you review and edit it (nothing auto-applies).
Download the document Export .docx ↓ — renders the official SFU .docx. Rendering only; nothing is validated or published.
Send for approval Submit for review → persists a draft into the queue, attributed to you. Publishes nothing (guardrail 1).

Scope: the Builder authors JDFN roles (APSA / APEX / Polytechnic). CUPE roles use a different instrument (WJQ) with no ratified quality bar yet, so they are deliberately not authorable.

05

Reviewing & approving — the Review queue

📋

Review queue

✔ Reviewer or admin

Where: /jd-bank/ui/queue — an author who isn't a reviewer is turned away here.

TaskHow
See what's awaiting review Open the queue — a list of draft canonical JDs.
Inspect a draft Click a row: the rendered draft, the harmonization change-log (what each source fed, what was dropped and why), and the live gate decision.
Approve Approve (fill an override reason for any overridable blocking gate). Publishes only if the validator's gates permit, re-checked at approve time — a blocked draft can't be approved without a valid override.
RejectReject + a reason.
Edit Edit the content + a reason — creates a new draft version; the prior is archived.

The reviewer on every action is the authenticated user — there is no "type your id" field. Every action is written to the tamper-evident audit log.

06

User management

👤

User management

🔑 Admin only

Where: /jd-bank/ui/admin/users — the 👤 Users link appears only if you're an admin.

TaskHow
See everyone Table of every user who has signed in (provisioned on first login) — roles, status, last login.
Grant / change roles Tick author / reviewer / admin → Save roles (e.g. make a hiring manager a reviewer so they can approve).
Disable an account Disable — blocks login and revokes live sessions (signs them out everywhere).
Re-enableEnable.

Self-lockout guards: you can't remove your own admin role, nor disable your own account — so a single-admin deployment can't brick itself.

Operator tasks — pipelines, deploy, config

🖥️

Server / operator

🖥️ Server access — not the app admin role

Run on the server shell (Docker-only). The app admin role does not grant this.

Bring-up & schema

CommandWhat it does
make upStart the stack (Postgres, Neo4j, Redis, api, worker).
make migrateApply DB migrations — run before ingest. Includes auth tables + the audit hash-chain.
make shellOpen a shell inside the app container.

The archive pipeline — in order

CommandWhat it does
make ingestLoad + parse the archive into Postgres. Incumbent names scrubbed at ingest.
make embedSection + document vectors into Neo4j (self-hosted Ollama, local-only).
make near-dupTier-2 near-duplicate dedup.
make dedup-roleTier-3 role-equivalence dedup.
make clusterCluster roles (Phase-3.5 report).
make canonical-draftsOne draft canonical per JDFN cluster into the review queue.
make baselineScore the whole archive; writes docs/baseline/.

Governance, health & auth config
