# P0.4 — The production posture, actually in force

**Priority:** P0 — the top of the queue. **Status:** open.
**Promoted:** 2026-08-13, by P0.3 part 2's answer: `sfuai.ca:7000` **is internet-facing**.

## Why this is P0 now and was not before

P0.2 built a fail-closed production guard: in `environment=production` a `Settings` that
would leave the service open does not construct, so the process dies rather than serves.
It has been correct and inert, because nothing runs in `production`.

P0.3 established that the deployment is **public**. So the one deployment that most needs
that guard is the one running without it:

- served over **plain http at a public DNS name** — session cookies and CAS tickets, both
  live credentials, cross the open internet in the clear;
- `environment=development`, so none of P0.2's nine conditions are enforced;
- the committed `app` / `harnesspass` credentials are still in place (no longer reachable
  from off-host since P0.3 bound the data ports to loopback, but still not secrets).

## ⚠️ The trap this task exists to avoid, MEASURED

`api` runs `uvicorn … --reload`. A settings refusal under the reloader does **not** kill
the container. Measured against this repo's own image, `ENVIRONMENT=production` with the
committed dev values (five conditions unmet):

| command | outcome |
|---|---|
| `uvicorn src.api.main:app --reload` | prints `Application startup failed. Exiting.` and **stays alive** — still running when killed at 45s (exit 124). The container reads **`Up`** and serves nothing. |
| `uvicorn src.api.main:app` | exits **3** promptly. The container dies; an orchestrator, a healthcheck and `docker compose ps` all see it. |

That is the P0.2 failure mode one layer down: a control that is correct, enabled, and
invisible. **The fix is already the image's default** — `core/Dockerfile`'s `CMD` carries
no `--reload`; only the dev compose overrides it. So the production overlay does not add a
command, it *stops overriding* one.

## ⚠️ The obvious shape does not work, and that was measured too

The natural design is an **overlay** (`-f docker-compose.yml -f docker-compose.prod.yml`)
that turns off the dev-only parts. It cannot: **15 services bind-mount `./core:/app`**, and
compose *merges* volume lists rather than replacing them. Rendered with an overlay
declaring `volumes: []`, the base mount is still there:

```
$ docker compose -f docker-compose.yml -f overlay.yml config
    volumes:
      - type: bind
        source: C:\repos\JD-Assistant\core
        target: /app          # ← still mounted
```

So an overlay cannot deliver *"the image is what runs"* — the single property that
separates a deployment from a working tree. **P0.4 therefore ships a standalone
`docker-compose.prod.yml`**, used alone rather than layered.

Duplication is the cost, and it is paid with a test rather than with discipline: the prod
file's settings-bearing services and env keys are **derived from the base file** and
asserted to cover it, so a key added to `&app_env` tomorrow fails the suite until the
production file carries it too. (Restructuring the base so that dev *adds* the mounts was
considered and rejected for this task: every `make` target and every developer's muscle
memory assumes the default file, and rewiring that under an internet-facing deployment is
not the change to make in a hurry.)

## Scope

1. **A standalone production compose file** (`docker-compose.prod.yml`, used as
   `docker compose -f docker-compose.prod.yml up -d`):
   - `api` / `worker` / pipeline services: **no `command:`** (inherit the image CMD, so no
     `--reload`), **no `./core:/app` bind mount** (the image is what runs, not the working
     tree), `restart: unless-stopped`.
   - `ENVIRONMENT: production` pinned — the overlay *is* the opt-in.
   - Secrets carry **no dev default**: `${DATABASE_URL:?…}` so compose refuses to render
     without them, rather than silently supplying the committed one.
   - A **healthcheck** on `api` (`/health`), so "up" means "answering".
   - `api` bound to loopback, with TLS terminated in front of it.
2. **Tests that read the overlay**, because an unverified overlay is the same hole one
   file over: no `--reload` anywhere, no source mounts, every settings-bearing service
   covered, every credential unset-by-default, the Dockerfile CMD still reload-free.
   Prove them failing by mutation.
3. **Docs**: what the operator must supply that this repo cannot — TLS at the edge, real
   secrets — and the deploy command.

## Explicitly NOT in scope

**TLS termination itself.** The public name is a forward we do not control; a certificate
and a terminator are a deployment decision. What this task owes is (a) an app that is
correct behind one — P0.3's origin allowlist already reads `X-Forwarded-Proto` and
validates the result — and (b) a posture that refuses to run pretending otherwise.

## Definition of done — ✅ met, and shown by deploying it

Brought up as its own compose project on separate ports, so the live dev stack was never
touched, then torn down with `down -v`.

**A safe posture serves:**

```
api: Up 8 seconds (healthy)      neo4j: Up (healthy)
postgres: Up (healthy)           redis: Up (healthy)     worker: Up
$ curl 127.0.0.1:35800/health -> {"status":"ok"}
$ docker inspect … .Config.Cmd -> ["uvicorn","src.api.main:app","--host","0.0.0.0","--port","8000"]
$ docker inspect … .Mounts     -> C:\repos\JD-Assistant\docs -> /docs (ro)
```

No `--reload`. The **only** mount is the read-only artifacts directory — the image is what
runs.

**An unsafe posture does not.** One condition flipped (`SESSION_COOKIE_SECURE=false`):

```
t+12s  state=restarting exit=3 restarts=8  health=unhealthy
t+48s  state=restarting exit=3 restarts=10 health=unhealthy
$ docker compose ps  ->  api: Restarting (3) 6 seconds ago
```

**Compose refuses to render without credentials:**

```
$ docker compose -f docker-compose.prod.yml config
error while interpolating x-app-env.DATABASE_URL: required variable DATABASE_URL is
missing a value: set DATABASE_URL to a database with a real password — the dev default
is committed to git, so it is not a secret
```

### One correction to this task's own wording, earned by running it

The DoD said the container would "**not be `Up`**". With `restart: unless-stopped` that is
not quite true and the difference matters: a crashing container is restarted, so a
*snapshot* of `docker compose ps` can catch it mid-cycle reading `Up (health: starting)`.
Watched for a minute it reads **`Restarting (3)`**, the restart count climbs, and the
healthcheck says `unhealthy` throughout. **The honest statement is that it never becomes
healthy**, and the healthcheck — not the status column — is what makes that legible. That
is the second reason the healthcheck is part of this task rather than a nicety.

## Two defects in this file, both found by deploying rather than reading

Recorded because they are the same class as the one this task exists for — a control that
looks right and is not reachable:

1. **`NEO4J_dbms_memory_heap__max__size`.** Neo4j maps `_`→`.` and `__`→`_`, so a stray
   underscore made it `dbms.memory.heap_max_size`, which Neo4j 5 rejects outright:
   *"Unrecognized setting"*. The container never became healthy and `api` never started.
2. **`cypher-shell -p $NEO4J_PASSWORD` in the healthcheck.** That variable exists in the
   *compose* environment and not inside the neo4j container, so it expanded to empty and
   the healthcheck failed authentication forever while Neo4j itself was perfectly fine —
   `NEO4J_PASSWORD=[] NEO4J_AUTH=[neo4j/…]`. It now reads the password out of
   `NEO4J_AUTH`, so the secret appears once.

Neither is visible in review; both are obvious on the first `up`.
