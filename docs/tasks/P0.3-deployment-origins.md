# P0.3 — Deployment origins: a CAS origin allowlist, and the external-exposure posture

**Priority:** top 10; sits directly after P0.0.
**Status: Part 1 ✅ DONE (2026-08-13). Part 2 ✅ ANSWERED — and the answer moves work.**
**Raised:** 2026-08-11, when the system was first reached from outside the dev box.

## ✅ Part 1 shipped

`allowed_service_origins` (env `ALLOWED_SERVICE_ORIGINS`, comma-separated) lists the
origins this deployment may return a browser to. `src/api/service_origin.py` reads the
origin the browser actually used — `X-Forwarded-Host` if a proxy set it, otherwise the
`Host` header — and returns it **only if it is on the list, exactly** (scheme, host,
port). Anything else falls back to `cas_service_base_url` and **never** to the header.

**Reading `Host` as well as `X-Forwarded-Host` is what the original bug required:** the
case that actually happened was a plain TCP port-forward, which sets **no proxy headers
at all**, so the browser's own `Host` was the only evidence of the origin it used.

**`cas_service_from_request` is RETIRED, and the field deliberately still exists** — a
deployment that sets it is now **refused at load in every mode**, with a message naming
`ALLOWED_SERVICE_ORIGINS`. Deleting the field would turn an operator's `true` into a
no-op they are never told about: a security change they believe they made and did not.
P0.2's production refusal is updated in the same change, as this task required.

Load-time validation: an entry that is not an origin (no scheme, a path, userinfo — note
`https://good.example@attacker.example` has the **attacker** as its host) is refused in
every mode, because it could never match and would silently reduce the deployment to the
static fallback. In production every entry must be https at a real hostname, exactly as
`cas_service_base_url` must; the shipped default is the committed dev origin, so a
production deployment that never set it is refused.

**DoD, met and verified against the running system** (not only in tests):

| Request to the live api | CAS `service=` |
|---|---|
| `Host: localhost:25800` | `http://localhost:25800/…` |
| `Host: sfuai.ca:7000` | `http://sfuai.ca:7000/…` |
| `Host: attacker.example` | falls back to the static origin |
| `X-Forwarded-Host: attacker.example` | falls back to the static origin |

Both origins now work **at once** — the repo-root `.env` gained
`ALLOWED_SERVICE_ORIGINS=http://localhost:25800,http://sfuai.ca:7000`, so **localhost
sign-in works again without unpointing the forward**. That retires the standing warning
at the top of `HANDOFF.md`.

### The `--proxy-headers` decision P0.0 handed here: **not needed. Closed.**

P0.0 deferred it deliberately — its scheme-blind `307` was a redirect problem, and buying
the fix with *trust in a forwarded header* is a decision this task owns. Having built the
allowlist, the answer is that uvicorn's flag is not required at all, and turning it on
would be strictly worse:

- **The CAS origin does not need it.** `service_origin.py` reads `X-Forwarded-Proto`
  **itself**, and the result is only honoured if the whole origin is on the allowlist.
  `--proxy-headers` would instead rewrite `request.url.scheme` **globally**, from a header
  nothing validates, for every consumer in the app — a wider grant to solve a narrower
  problem.
- **Redirects do not need it.** P0.0 made every redirect relative, so no redirect names a
  scheme to get wrong.
- **A proxy that sets no `X-Forwarded-Proto` degrades safely.** The derived origin is then
  `http://…`, which in production cannot be on the allowlist (https is required), so it
  falls back to the validated static origin rather than emitting a plaintext one.

The flag stays off. Should something later genuinely need a trustworthy `request.url.scheme`,
the decision to reopen is "which hop do we trust", and `--forwarded-allow-ips` — not
`--proxy-headers` alone — is the setting that answers it.

**One thing found on the way, and it is the kind that stays found:** the first run of
`test_service_origin.py` failed on the dev box and would have passed in CI, because the
repo-root `.env` points `CAS_SERVICE_BASE_URL` at the live demo forward and the `gates`
service passed it straight through — so "falls back to the static origin" was silently
asserting against whichever host the developer happened to be demoing. `CAS_SERVICE_BASE_URL`
and `ALLOWED_SERVICE_ORIGINS` are now pinned in the `gates` service alongside the data
stores, and listed in `GATES_HERMETIC_PINS` with the reason.

## What happened

The app was port-forwarded to a public name — `sfuai.ca:7000` → `25800`. Sign-in broke: CAS
authenticated the user, issued a ticket, and then sent the browser to
`http://localhost:25800/jd-bank/ui/cas/validate?...`, which means nothing to an external client.

Cause: the CAS return origin is a **single static setting**, `cas_service_base_url`, still pinned
to `http://localhost:25800`. Repointing it at `http://sfuai.ca:7000` fixed it immediately — and
that is a workaround, not a design.

Useful fact learned in passing: **SFU CAS accepted `http://localhost:25800` as a service and
issued a ticket**, so it is not strictly validating service URLs against a registry. We cannot
lean on CAS to reject a wrong origin for us.

## Part 1 — The CAS origin allowlist

### Why one static value is wrong, and why the obvious alternative is worse

A single origin cannot serve localhost, `sfuai.ca:7000`, and a future real hostname at once.
Today, switching between them means editing `.env` and restarting.

The code already has the obvious alternative: `cas_service_from_request` derives the origin from
`X-Forwarded-Host`. **It is a header-injection vector**, and P0.2 deliberately refuses it in
production: `X-Forwarded-Host: attacker.example` makes the CAS return URL attacker-controlled, so
an authenticated user is bounced to the attacker *with their ticket*, and `x-forwarded-proto`
defaults to `http`, so the derived origin can be plaintext even with secure cookies on.

So the two options as they exist are "rigid" and "exploitable". Neither is right.

### What to build

Derive the origin from the request, then **validate it against an allowlist**, and force `https`
in production. This is the alternative the security review named when it found the injection
vector; we took the blunt option then because nothing needed multi-origin. Now something does.

- A setting — e.g. `allowed_service_origins` — listing the origins this deployment may return to.
  Follow the shape of `allowed_inference_hosts`, which already solves the same problem for the
  NN #5 egress boundary: a list, with sane defaults, read through one guard.
- The derived origin must match the allowlist **exactly** (scheme, host, port). An unlisted origin
  falls back to the static `cas_service_base_url` — **never** to the request's own header.
- In production, force `https` and refuse a loopback/private origin, as `_unsafe_service_origin`
  already does for the static value.
- Then `cas_service_from_request` can be retired, or become an alias for "allowlist mode". Decide
  deliberately and record it — P0.2 refuses that flag in production today, so the refusal has to
  be updated in the same change or it will refuse the new mechanism too.

**DoD:** localhost and an external origin both sign in with no config change between them; an
origin not on the list is refused and falls back rather than being honoured; the P0.2 production
guard is updated coherently; and a test drives `X-Forwarded-Host: attacker.example` and proves
the return URL is unaffected.

## Part 2 — The external-exposure posture

Raised and **not yet answered**: the deployment is now reachable at a public DNS name over plain
**http**, while running in `environment=development`. That combination means:

- **P0.2's fail-closed guard is inactive.** Nothing is enforcing secure cookies, non-default
  secrets, TLS verification or a real CAS origin — those checks only fire in `production`.
- **Session cookies and CAS tickets cross the network in the clear.** A ticket is single-use and
  short-lived, but it is a live credential.
- **Database and Neo4j credentials are still the committed defaults** (`app` / `harnesspass`).
- **The data stores publish on `0.0.0.0`** — `25432` (Postgres), `25474`/`25687` (Neo4j), `25379`
  (Redis). **If port 7000 reaches this host from outside, check whether those do too.** This is a
  larger exposure than the CAS redirect that prompted the task.

### The decision needed

**Is `sfuai.ca:7000` internet-facing, or campus/VPN-only?**

- **Campus/VPN-only** — most of the above is acceptable for a demo. Bind the data ports to
  `127.0.0.1` anyway; it costs nothing.
- **Internet-facing** — then this should be running the production posture P0.2 was built for:
  TLS at the edge, `ENVIRONMENT=production`, real secrets, `SESSION_COOKIE_SECURE=true`, data
  ports closed. That is also the moment the missing **production compose profile** (P0.1b-ii)
  stops being a nice-to-have: the `api` service still runs `--reload`, which means a
  refuse-to-boot shows up as "Up but serving nothing".

**DoD:** the question is answered and recorded; data ports bound to loopback unless there is a
stated reason; and if internet-facing, the production posture is actually in force rather than
available.

### ✅ ANSWERED, 2026-08-13: **internet-facing.**

So the second branch above is the live one, and this stops being a hardening backlog item.

**Done immediately, and verified against the running stack:** Postgres (`25432`), Neo4j
(`25474`/`25687`) and Redis (`25379`) are bound to `127.0.0.1` in `docker-compose.yml`
and in the containers now running. Every one of them answered on `0.0.0.0` with a
credential that is **committed to this repo** — so the protection was never "an attacker
must guess a password", it was "nobody has looked". Docker writes its publish rule
straight into the host's forward chain, so the host firewall was not saving us either.
Pinned by `test_a_data_store_is_published_only_to_loopback`, which enumerates the
publishing services from the compose file and was **shown to fail** by republishing redis
on all interfaces.

**What that leaves open, stated plainly, because it is now the largest thing on the
board:**

1. **The app itself is served over plain `http` at a public DNS name.** Session cookies
   and CAS tickets — live credentials — cross the open internet in the clear. TLS at the
   edge is the fix, and nothing in this repo can do it; it is a deployment decision.
2. **`environment=development`, so P0.2's fail-closed guard is inactive.** Every
   condition it enforces — CAS on, real secrets, `SESSION_COOKIE_SECURE`, a real service
   origin — is unenforced on the one deployment that most needs them.
3. **The production compose profile (P0.1b-ii) is now a blocker, not a nice-to-have**, and
   is promoted to **P0** in `HANDOFF.md`. Note the trap it exists to avoid: `api` still
   runs `uvicorn --reload`, so a settings refusal in the reloader presents as **"Up but
   serving nothing"** rather than as a container that died — the P0.2 failure mode all
   over again, one layer down.
4. **The committed `app`/`harnesspass` credentials remain in place.** Loopback binding
   means they are no longer reachable from outside the host; it does not make them
   secrets. Real ones are part of the production posture in (3).

**Judgement:** the demo can continue on the current arrangement — it is a JD archive, the
approval path is gated, and nothing publishes without a reviewer — but it should not be
left standing as the pilot deployment. The next task is (3), and it is P0.

## Why this is top-10 and not P0

The immediate breakage is fixed — sign-in works through the forward. What remains is that the
mechanism is brittle and the posture is undecided. Neither blocks the pilot today, and both get
much more expensive to fix after someone depends on the current arrangement.
