# P0.0 — Navigability: no dead ends anywhere

**Priority:** top of the backlog, ahead of P0.1b-ii. **Status:** open.
**Found:** 2026-08-11, live, minutes before an HR demo.

## What happened

Someone typed the address of the system into a browser:

```
http://localhost:25800   →   {"detail":"Not Found"}
```

`/jd-bank/ui` does the same. The application only serves specific deep paths — the shallowest
thing that works is `/jd-bank/ui/library`. A first-time visitor, or anyone who bookmarks the host
rather than the page, lands on a raw JSON error.

That is not a missing redirect. It is three separate gaps that happen to meet at the front door,
and each has its own way of biting us again:

1. **There is no landing route.** Nothing answers at the root.
2. **Errors are not written for humans.** A browser rendering `{"detail":"Not Found"}` is what
   every 404, 403 and 500 looks like on a UI path, including the CSRF/stale-tab 403 that now
   fires after a long-open tab.
3. **Nothing tests that a link goes anywhere.** Every `href` in every template is unverified. A
   Jinja-built path with one wrong segment ships silently, and only a human clicking it finds out.

## Why this is P0

The pilot is the critical path, and the pilot is a person clicking around unsupervised. A reviewer
who hits a JSON blob does not file a bug — they lose confidence in the system. It is also cheap:
the whole class is a landing route, two error templates, and one crawl test.

## Scope

### 1. A landing route
`GET /` resolves to something sensible for both an authenticated and an anonymous visitor. The
library is the natural home (`🏦 JD Bank` is already the first nav item), but decide deliberately
whether the root **redirects** or **renders** — an anonymous visitor typing the bare host should
get a sign-in path, not a redirect chain that dead-ends. Cover the obvious near-misses too:
`/jd-bank`, `/jd-bank/ui`, and trailing-slash variants.

### 2. Human-readable error pages
404, 403 and 500 on a **UI** path render an HTML page in the app's own chrome, with the nav and a
way back. JSON paths keep their JSON — the distinction is the content type the caller asked for,
not a hardcoded list of prefixes.

The 403 page needs specific copy for the case that will actually occur most: **a stale tab after
CSRF landed**. "Reload this page and try again" — not "Forbidden".

### 3. A crawl test — the durable artifact
Render every UI page as each role, extract **every `href` and `form action`**, resolve them
against the live routing table, and fail if any 404s. This is the piece that stops the class
recurring, and it should be built the way the other safety nets in this repo were built after
each of them shipped green over a hole:

> **Enumerate from the live artifact, never from a hand-maintained list.** The authorization
> matrix walks the real routing table; the compose-delivery pin derives its required set from a
> real refusal message. This test should walk the real rendered HTML.

Prove it fails: point a template link at a nonexistent path and show the test go red.

### 4. Sweep the non-404 dead ends
A page that renders but strands the user is the same defect wearing a different status code:
pagination past the last page, a detail page with no way back, an ID route given a valid-but-
missing UUID, a search with no results and no next step.

## Constraints

- **Any new route needs an entry in `core/tests/unit/test_authorization_matrix.py`** — the
  completeness assertion fails otherwise, by design — **and in the CSRF table** if it changes
  state. That is the cost of the landing route and it is the correct cost.
- Decide the landing route's access deliberately. It is the one page an anonymous visitor sees,
  so it belongs in `PUBLIC_STATE_CHANGES`-adjacent thinking: public, or a redirect to sign-in.
- Not register-bearing. No rulebook change; `rules_version` must not move.

## Definition of done

- Typing the bare host reaches something useful, signed in or not.
- No UI path returns raw JSON to a browser.
- The stale-tab 403 tells the reader to reload.
- A crawl test fails when any rendered link 404s, and has been shown to fail.
- The audit's inventory is either fixed or explicitly deferred with a reason.

## Evidence — the crawl (2026-08-11)

Crawled in-process against the real app: 51 served routes, unauthenticated and as admin /
reviewer / author, plus a method-aware scan of all 19 templates.

**The good news, so it does not get re-litigated:** **zero broken template link targets.** Every
`href` and `form action` resolves to a real route with the right method, including all the
Jinja-interpolated ones. No route shadowing. Trailing slashes work. Pagination cannot 404 past the
end. Valid-but-missing UUIDs on `/role/`, `/jd/`, `/review/` already render a friendly HTML page —
**that is the pattern the rest should copy.**

### Polish
Malformed ids (`/role/not-a-uuid`) and `?limit=abc` return raw pydantic `422` dumps instead of the
friendly page a *missing* UUID already gets · `/favicon.ico` and `/robots.txt` 404 on every page
load, with no `StaticFiles` mount anywhere · the **login page renders the full authenticated nav**,
whose five links all loop back to the login page · the guide's fallback is a bare `<h1>` fragment
with no shell.

## The classes to fix

1. **No front door** — nothing at `/`, `/jd-bank`, `/jd-bank/ui`.
2. **Errors are JSON on an HTML surface.** The auth matrix correctly distinguishes JSON from UI
   surfaces for the **status code**; nothing makes that distinction for the **body**.
3. **The nav is not role-aware.** Authorization is right; *affordance* is not.
4. **A write succeeds and lands the user somewhere they cannot go.**
5. **Two 404 idioms coexist** — four routes render a friendly page, two raise bare JSON.
6. **Empty states live inside the "has items" branch** — one template shape, three symptoms.
7. **No static surface**, so browser-automatic requests are unhandled 404s.
8. **Redirects are absolute and scheme-blind** without `--proxy-headers`.

## Judgement: redirect, not a landing page

A `303 /` → `/jd-bank/ui/library` is right — verified for both personas, including the signed-out
chain through login and back. A bespoke landing page would duplicate the library's own intro and
be one more surface to keep true.

**But the redirect alone leaves it half-fixed:** every other typo still returns raw JSON, and the
signed-out visitor lands on a login page whose entire nav is a no-op. Ship the redirect, the HTML
error handlers, and the role-aware nav together.
