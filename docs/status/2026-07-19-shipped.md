## The headline

**The full pipeline now exists end to end — a cluster of duplicate JDs goes in, a single harmonized
DRAFT comes out, and a human HR reviewer approves / edits / rejects it through a UI. Nothing publishes
unless a human approves a gate decision that already permits it.** The only piece of Phase 4 left is
the pilot with a real reviewer (4.5).

| Stage | What it does | Publishes? |
|---|---|---|
| **4.1 merge** | cluster → deterministic DRAFT (section select, duty union/dedup, KSA rebuild) — no LLM | never |
| **4.2a rewrite** | DRAFT → cleaner prose via self-hosted LLM, under an anti-fabrication guard | never |
| **4.2b audit** | advisory inclusive-language / clarity / seniority findings — **no score** | never |
| **4.3 change-log** | per-source diff: which member fed which section, what was dropped and why | never |
| **4.4a producer** | drives 4.1→4.3 per cluster, persists a DRAFT `canonical_jds` row | never |
| **4.4b service** | list / packet / **approve** / reject / edit / override — the approval spine | **only path** |
| **4.4c routes** | thin HTTP over the service | — |
| **4.4d UI** | queue → detail (draft + diff + report) → approve/edit/reject/override buttons | — |

## For HR — the one thing that matters

**The approval bar did not move, and it cannot be moved by this work.** Phase 4 is about *combining*
duplicate JDs and *routing them to a human* — it adds **no new scoring rule and changes no threshold**
(every new config file is registered but deliberately excluded from the rulebook digest, because how
JDs are merged is not how a JD is scored). The 874-JD current-practice baseline (78.6% approval) stands
untouched.

**And the non-negotiable holds by construction: nothing auto-publishes.** A canonical JD is a DRAFT
until a reviewer clicks approve, and the system *refuses to publish* unless the gates already permit it
— re-checking the JD's current content at approve time, never trusting a stored verdict. Waiving a gate
requires a written reason, recorded in an append-only audit log. **The next step is putting 5–10 of
these in front of a real HR reviewer (4.5).**

## For the team — what actually shipped

### 4.1 · Merge engine + calibration (PR #46)
Pure, LLM-free `bank/merge.py`: section selection, duty union/dedup/reorder, KSA rebuild — drafts only,
no approval field. **9 knobs** in registered/unhashed `harmonization.yaml` (HR-167..175). Calibrated by
running the merge over **1,801 real JDFN clusters** (the `jd_bank/harmonize/` measurement runner); one
default moved on evidence (`max_duties` 10→12, aligned to the model's own cap), the other 8 kept as
measured-well-placed. **%-rebalance of duty allocations is deferred** (allocations are free-text, not a
structured field).

### 4.2 · The two LLM passes (PRs #49, #51)
Both run on **self-hosted Ollama (`gpt-oss:120b` on `aria-gb10-2`)** — no vendor egress of JD content.
- **4.2a rewrite** rewords the grounded 4.1 draft under an **anti-fabrication guard** (ungrounded
  skill/knowledge/ability quals are scrubbed; invented duties flagged), then scores the result with the
  deterministic validator. Output is an explicit DRAFT.
- **4.2b audit** is a **nuanced, advisory** pass (inclusive language / clarity / seniority mismatch) with
  a **verbatim-evidence scrub** — any finding whose quoted evidence is not literally in the JD is
  dropped. It computes **no score or grade**; the deterministic validator stays the sole oracle.

### 4.3 · Change-log / diff (PR #52)
Pure `bank/change_log.py::build_harmonization_diff` → a frozen `HarmonizationDiff`: the rendered draft,
per-source contributions (which member fed which section), a removed-content log (what was dropped and
why), and flagged duties. Drop-vs-dedup is authoritative from the merge's *actual* cap-dropped groups —
not a similarity proxy (the reviewer proved the proxy mislabels duties). This is what a reviewer reads
to trust a merge.

### 4.4 · The review queue (PRs #53–#56)
The human-approval spine, sliced producer → service → routes → UI.
- **4.4a producer** turns JDFN clusters into persisted DRAFT `canonical_jds`. **Idempotent** (stable
  content-derived cluster id) and **no-clobber**: a canonical a reviewer has already touched is never
  overwritten. Append-only audit per persist.
- **4.4b service** is where non-negotiable #1 lives. **approve** re-validates the canonical's *current*
  content, evaluates the gates, applies any overrides, and publishes **only if the decision permits** —
  otherwise it raises and writes nothing. An override needs a written reason. An edit mints a new DRAFT
  version and archives the prior. A `FOR UPDATE` lock serializes approvals.
- **4.4c routes** expose the service over HTTP as a `/jd-bank` router; transport only (typed errors →
  status codes), no invariant logic in a handler.
- **4.4d UI** is a minimal server-rendered review UI *inside* FastAPI (`/jd-bank/ui`) — chosen over the
  untested Flask frontend so the approval surface stays under the test gate. Queue → detail → approve/
  edit/reject/override. No JS build step, no new runtime dependency.

## What's next / open

- **4.5 — the pilot.** 5–10 clusters end to end with a real HR reviewer through the 4.4d UI; every bug
  becomes a regression fixture. This is where the ~24 provisional `open` defaults from 4.1–4.4 (all of
  `harmonization`/`rewrite`/`quality`.yaml) get calibrated against human judgment.
- **Pre-pilot engineering follow-ups:** split the rewrite/audit LLM clients before the two YAMLs diverge
  (provenance); a runner to produce change-logs over real clusters; a per-section merge policy for the
  four sections 4.1 leaves at model defaults (the `sections_not_merged` flag fires on 97.8% of clusters).
- **Op note:** 4.4d was **merged locally** — GitHub Actions was billing-blocked at merge time, so its
  CI could not run (local `make gates` is CI-identical per ADR-006). **PR #56 is open and unmerged on
  GitHub; re-run its CI and reconcile `main` once billing is restored.**

**Nothing auto-publishes. Canonical JDs remain drafts until a human approves them.**
