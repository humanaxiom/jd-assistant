# Shipped — 2026-07-24 · Phase 5: the JD Builder / Composer (COMPLETE on `main`)

The one-pager for catching up. Phase 5 — the project's **first forward-looking, user-facing
product** — is complete and fully on `main`. Everything before this analysed the *existing*
archive; the Builder helps a hiring manager/recruiter **author a new SFU-compliant JD**.

## What a user can now do, end to end

1. **Find** an existing JD to start from — semantic search over the embedded archive
   (`GET /jd-bank/compose/search`) and clone it into the guided form
   (`GET /jd-bank/compose/clone/{id}`).
2. **Compose** — a guided question flow (`/jd-bank/ui/compose/new`) sourced from the SFU
   Toolkit, assembled deterministically into the JD contract.
3. **Validate live** — `POST /jd-bank/compose/validate` shows compliance as you write:
   *still-to-write* (guidance) vs *present-but-non-compliant* (findings), per-section
   state, word/duty meters — computed by the **real validator** (NN #3).
4. **Get an LLM assist** — `POST /compose/assist/summary` rewrites the Position Summary
   to the 100–150-word standard, grounded, and re-validated (self-hosted, NN #5).
5. **Export** — `POST /compose/export` renders the official SFU `.docx` (TNR-10, bold
   headers, bullets, rulebook footer).
6. **Submit** — the draft enters the **same HR review queue** as the harmonized drafts;
   the 4.4b service is the only publish path (NN #1). Nothing auto-publishes.

Every page of the server-rendered UI now carries a **nav bar** (Builder · Review queue ·
Dashboards) — the features were previously reachable only by typing URLs.

## ⚠ Scope: the Builder is JDFN-only, and CUPE is deliberately OUT (HR-194)

**This is the single most important thing to state before anyone assumes the Builder covers
all SFU JDs. It does not.** It authors the **JDFN template only — APSA / APEX / POLY**.

**CUPE is ~29.5% of the archive (~4,300 files on the WJQ instrument) and is deliberately not
served.** The reason is not neglect: there is **no ratified CUPE quality bar**, so the
validator — the oracle for everything the Builder does (NN #3) — can only score the JDFN
template. Offering to author a CUPE JD would guarantee a **category-error mis-score** on the
JDFN gates (the same error HR-143 keeps out of the baseline cohort). Exempt/`excluded`
executives are out for the same reason.

The scope used to be a hardcoded tuple in `compose_ui.py`; it is now
`segmentation.yaml :: jdfn_employee_groups` (rulebook-as-data, NN #2), read by the UI, and
**registered as an open HR decision, HR-194**: *should CUPE/exempt roles stay out until HR
defines a bar for them?* **To serve CUPE, HR must define a CUPE bar first** (a WJQ ruleset
with an oracle); only then does a token get added to that list. Tracked on the Phase 7
roadmap; nothing about it is decided by omission.
